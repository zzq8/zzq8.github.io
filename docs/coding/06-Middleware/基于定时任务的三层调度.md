## 哪三层 - 1
优势：通常是指在一个系统或平台中，为了**高效、有序地执行**各种定时触发的任务，而设计的一种**<font style="color:#DF2A3F;">层次化的任务调度机制</font>**。这种机制可以确保任务按照优先级、资源可用性以及业务需求被合理安排和执行。提升执行效率，在分布式架构中尤为重要。

1. **<font style="background-color:rgb(247, 249, 253);">第一层：任务规划层 -  TODOList</font>**
    - <font style="color:rgb(51, 51, 51);background-color:rgb(247, 249, 253);">在这一层，主要负责定义和规划所有需要定时执行的任务，包括任务的创建、修改和删除。每个任务会设定具体的执行时间（如每天几点几分）、执行周期（如每天、每周、每月等）以及任务的描述和相关参数。这一层的作用是为整个调度系统提供清晰的任务清单和执行计划。</font>
2. **<font style="background-color:rgb(247, 249, 253);">第二层：任务优先级与资源分配层 - OrderList</font>**
    - <font style="color:rgb(51, 51, 51);background-color:rgb(247, 249, 253);">当多个任务同时或接近同一时间需要执行时，这一层负责根据任务的优先级（紧急程度、业务重要性等）、所需资源（CPU、内存、网络带宽等）进行合理的调度安排。它确保高优先级的任务能够优先执行，同时考虑系统的整体负载均衡，避免资源过度集中导致的系统瓶颈。这层可能会涉及复杂的算法来优化任务的执行顺序和资源分配策略。</font>
3. **<font style="background-color:rgb(247, 249, 253);">第三层：执行与监控层 - execute</font>**
    - <font style="color:rgb(51, 51, 51);background-color:rgb(247, 249, 253);">到达这一层的任务将被实际执行。这一层负责根据前两层的信息启动相应的任务进程，并监控任务执行状态，包括任务是否成功完成、是否有异常、执行耗时等。如果任务执行失败，可能需要重新调度或触发告警机制。此外，这一层还会收集执行数据，为后续的调度优化提供反馈信息。</font>

### <font style="color:rgb(0, 0, 0);">什么是三层分发</font>
![](https://image.233377.xyz/2026/5b4e2eab73698bd1564bf60b56fff22c.png)

<font style="color:rgb(0, 0, 0);">这个图实际上描述了三层分发的过程：</font>

+ <font style="color:rgb(0, 0, 0);">通过消息驱动调用</font>
+ <font style="color:rgb(0, 0, 0);">splitor将任务分配给N台机器</font>
+ <font style="color:rgb(0, 0, 0);">loader获取数据后同样将任务分配给X台机器</font>

### <font style="color:rgb(0, 0, 0);">三层分发提供能力</font>
<font style="color:rgb(0, 0, 0);">三层分发是</font>**<font style="color:rgb(0, 0, 0);">sofa-platform-schedule</font>**<font style="color:rgb(0, 0, 0);">提供的能力，我认为三层分发提供了两个能力：</font>

+ <font style="color:rgb(0, 0, 0);">1.将任务拆解到不同机器上执行，将机器资源利用起来。</font>
+ <font style="color:rgb(0, 0, 0);">2.再利用资源的同时避免重复执行任务。</font>

# Total - 三层分发？可能这篇就够了
![](https://image.233377.xyz/2026/bd546422d85e9492d3933080cd002a8f.png)


**三层分发概述**  
**作用：**  
将任务拆解到不同机器上，充分利用集群服务器资源，从而支撑在集群环境下的大数据量的处理能力。如在 splitor 层将任务拆成了 n 份，在 loader 层将任务拆成 m 个业务，那么整个三层分发的作用相当于利用集群能力并发地处理 n*m 个业务，还是相当高效的  
**常见疑惑**  
Q：为什么是三层分发？不是两层？  
asplitor 拆分分发，一方面是把数据捞取的负载均摊开，不论是捞取大量任务占用的内存还是捞取后的处理所消耗的时间，都可以分到多台机器；另一方面也可以在发生异常时降低影响范围，分摊风险。所以，任务拆分只要保持负载在单机承受范围内，风险也相对有所下降，划分任务个数就好。loader 数据捞取后的分发，自然是为了任务执行的负载均摊。因为 tr 的 oneway 调用开销较小，又是在自己本 zone 调用，所以代价不大。总结来说就是如果直接 Splitor 层是单台机器实行的，如果直接捞取所有数据到 executor 层的话，代价大且没有充分运用好集群能力。  
b两层在一些业务下还真可以，不是所有业务都数据量大到要用三层分发的。看到一个讨论中的实现是“通过并发参数，限制第1层返回的List数量，减少2层的并发数，比如设置并发2，实际的100个分表任务就50个一组，只返回两个DataLoadFilterItem，第2层，dataLoader每捞一批数据，就循环把executor的事做了，不触发第3层，所以整体的并发数小于等于2层的消息数线程池大小”，而在 appxcore 的代码实现中，有另外一种可能更简单的方式就是直接在 Splitor 层不做拆分。之所以还用三层分发框架的原因是没必要再自己造一个轮子，根据业务情况看看是在 Splitor 层还是 Loader 层修改就好了

**关于 tr Oneway（关注负载均衡问题）**  
tr oneway <font style="color:rgb(38, 38, 38);">消费方调用后就返回，并不关心调用结果，框架会忽略提供方的处理结果</font>  
<font style="color:rgb(38, 38, 38);">三层分发通过tr的</font>**<font style="color:rgb(38, 38, 38);">负载均衡</font>**<font style="color:rgb(38, 38, 38);">能力进行任务的下发和执行。</font>  
**CE v4.4.2.0+ 或者 SOFA-RPC v4.10.0+**  
●负载均衡算法是随机选择。  
●考虑服务提供者的长连接情况：也就是说，在服务提供者挂掉，注册中心还未通知服务调用者摘除节点的这段时间里，调用者能提前感知提供者的长连接已经断了，将不再调用这个提供者，从而提高了系统的可用性。  
●考虑服务提供者的权重：假如一个服务有两个服务提供者，提供者 A 的权重是 100，提供者 B 的权重是 200，那么调用者对 A 和 B 的请求比例接近 1 : 2  
**CE v4.xxxx**  
后续会提供更多的负载均衡算法，例如：  
●轮询  
●本地最小并发  
●一致性hash  
●智能断路等
